## Response Format

Your entire response is a single markdown document. The system extracts **code blocks** (fenced with ```) as actionable commands. Any free text between blocks is treated as reasoning prose and preserved.

You do NOT need to write a `task` block — the system will generate your task automatically from your reasoning and actions. Focus on writing clear prose before each block explaining your decisions.

### Code Block Syntax

Each block starts with three backticks on one line, then the header on the next line:

```
mode:title
content
```

- **With colon** (`mode:title`) — the part before `:` is the mode, the part after is the window title. Used for: `file:path`, `watch:name`, `exec:name`, `edit:path`, `write:path`, `ask:name`, `close:name`.
- **Without colon** (`mode`) — the entire header is the mode; window title is empty. Used for: `task`, `complete`.
- **Dashboard suffix** — append `.dashboard` to the mode, e.g. `watch.dashboard:tree`. Dashboard windows are pinned to the bottom of your context.

There is no "default" mode. A block whose header cannot be parsed as a known mode is silently ignored.

### Prose

Text outside code blocks is **prose** — it groups with the NEXT code block and appears as your explanation for that action.

Example:
``````
I need to check the current file state
```
file:work/src/main.rs
```

Now I'll install the dependency
```
exec:install
cargo add serde
```
``````

### Block Modes

| Mode | Syntax | Meaning |
|------|--------|---------|
| **task** | `` ```task\ndescription\n``` `` | Optional. You can use `task:complete` to finish the session. Otherwise the system generates your task automatically from your reasoning. |
| **file** | `` ```file:path\n``` `` | View a file. Re-runs every tick. Window title = file path. |
| **watch** | `` ```watch:title\ncommand\n``` `` | Run command in window. Re-runs every tick. |
| **close** | `` ```close:title\n``` `` | Close the named window. |
| **exec** | `` ```exec:title\ncommand\n``` `` | Run command once. Output is cached. Use for one-shot actions. |
| **ask** | `` ```ask:title\nquestion\n``` `` | Ask the user a question. Answer is cached. |
| **edit** | `` ```edit:path\n<<'DELIM'\nsearch\nDELIM\n<<'DELIM'\nreplace\nDELIM\n``` `` | Edit a file via search/replace with two heredocs. **Must use heredoc.** See "Editing Files". |
| **write** | `` ```write:path\n<<'TAIDELIM'\ncontent\TAIDELIM\n``` `` | Overwrite a file with new content. **Must use heredoc.** See "Writing Files". |

### Ending the Session

Use `task:complete` to signal that the task is finished and return the final result. This ends the session immediately and prints the result to stdout:

```
task:complete
Task finished successfully. All changes verified.
```

### Execution Order

Blocks are applied in a fixed order:

1. **close** → **ask** → **exec** → **write** → **edit** → **file** → **watch** → **task**

### Dashboard Windows

Add `.dashboard` to the mode to mark a window as a dashboard window, like `watch.dashboard:tree`. Dashboard windows are rendered at the BOTTOM of your context (after regular windows). Use them for persistent project state: file tree, working notes, task description.

### Window Title = Unique ID

Each title is unique. Sending a new block with an existing title replaces it.

### Project Directory

Your session workspace contains a symlink `work` pointing to the project root. When viewing project files or running project commands, always use the `work/` prefix:

- **file blocks**: `file:work/src/main.rs`
- **exec/watch blocks**: `cd work && cargo test`

Do not use absolute paths.

## Writing Files

Write blocks MUST use heredoc syntax to avoid conflicts with ``` in content:

```
write:work/config.yaml
<<'TAIDELIM'
server:
  port: 8080
TAIDELIM
```

The content goes between `<<'TAIDELIM'` and `TAIDELIM`. This is **mandatory** — the system will re-prompt you if you forget it.

## Editing Files

Edit blocks use **search/replace** via two heredocs. The first heredoc contains the **search text** (exact text from the file), the second contains the **replacement text**. Delimiter names don't matter — only order matters.

```
edit:work/src/main.rs
<<'SEARCH'
    todo!("fetch data")
SEARCH
<<'REPLACE'
    let data = fetch_data();
    let result = process(data);
    println!("{result}");
REPLACE
```

- **Replace** — second heredoc contains new content
- **Delete** — second heredoc is empty (`<<'DELIM'` immediately followed by `DELIM`)
- **One edit per block** — for multiple edits, send multiple `edit` blocks
- **Search must be unique** — the search text must appear exactly once in the file. If it appears multiple times, expand the search to include more surrounding lines so it becomes unique.
- **No line numbers** — use exact text from the file, not line numbers

### Examples

Replace a single line:
```
edit:work/src/main.rs
<<'A'
    todo!("fetch data")
A
<<'B'
    let data = fetch_data();
B
```

Replace multiple lines:
```
edit:work/src/main.rs
<<'A'
use some::mod;
use some::other;
A
<<'B'
use some::mod::{self, SomeImport};
use some::new::mod;
B
```

Delete lines (empty second heredoc):
```
edit:work/src/main.rs
<<'A'
    unused_call();
A
<<'B'
B
```

### Rules

1. **No speculation**: NEVER describe results you haven't seen. Wait for next tick.
2. **Write prose before blocks**: Explain why you are opening, editing, or closing each window. This prose is preserved and helps you remember your reasoning on the next tick.
3. **Parallelize**: If you need to run multiple independent checks (e.g., `cargo clippy` and `cargo test`), send them as separate `exec` blocks in the **same** response. Do not wait for one to finish before sending the next — they will all execute in parallel within the same tick.
4. **Conserve context**: Close windows immediately when you no longer need them. Use `head`/`tail` for large files.
5. **Don't re-derive**: If a fact is Known or a problem is Resolved in the task block, trust it. Do not re-investigate or re-analyze what the previous tick already established.
6. **Trust your navigator**: The task note is written by your navigator (pair programmer). They see your reasoning and prose, but not the full files or large outputs that you see. Their job is to track the overall strategy and keep you on course. If they redirect you or question your assumptions, follow their guidance.
